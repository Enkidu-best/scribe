## А. «There is no Stream(gpu, 1) in current thread» - одна нить для MLX

Причина (практика: vllm-mlx `bind_generation_streams`, mlx-lm #1179, mlx-audio #744): потоки вычислений MLX привязаны к нити. Scribe грузит модель и прогревает её в одной нити (`_probe_engine` / прошлый `_worker`), а распознаёт в новой нити `_worker`, которая создаётся на каждый запуск. Модель в `ModelHolder` остаётся от прошлой нити - и вторая попытка падает. Особенно после ошибки.

Сделать:
1. Все вызовы MLX (прогрев, распознавание, детектор языка, диктофон) - в **одной долгоживущей нити-исполнителе** движка (`engine.MLXExecutor`, очередь задач). Нить GUI и `_worker` только ставят задачи и ждут результат. Альтернатива, если исполнитель неудобен: на входе каждой задачи - новый поток `mx.new_stream(mx.gpu)` по умолчанию для нити и перезагрузка модели, если она загружена в другой нити.
2. После любой ошибки распознавания - `unload()` и чистый `mx.clear_cache()`, следующий запуск начинается с чистого состояния.
3. Это же правило - в общий блок «Распознавание речи» (стандарт, раздел 7): Interview Coach и Herald (MLX в нитях) проверить на ту же ошибку.
4. Тест: подряд 3 запуска одного файла; запуск после искусственной ошибки; распознавание после диктофона; файл во время работы диктофона. Ни одного «no Stream».

## Б. Длинные файлы - по практике WhisperX (решение Андрея 19:16)

**Практика.** WhisperX (Bain и др., Interspeech 2023, arXiv 2303.00747): запись режется детектором речи (VAD) на куски около 30 с строго по паузам («cut & merge»), куски распознаются **пачкой** параллельно. Итог на TED-LIUM: примерно в 12 раз быстрее обычного Whisper, ошибок слов меньше (9,7 % против 10,5 %), меньше выдуманных фраз и повторов на тишине. Связь «текст прошлого куска → следующий» не используется - авторы нашли, что она чаще порождает повторы; Scribe и сейчас её выключает (`condition_on_previous_text=False`), так что единство текста от нарезки не страдает. Говорящие определяются **по всему файлу целиком** отдельным проходом и потом сопоставляются с фразами по времени - путаницы между кусками нет.

Сделать:
1. Сначала описание (Функциональное описание Scribe, раздел «Расшифровка файла»: этапы, состояния, продолжение) и запись решения в Единый стандарт, 7.1: длинные файлы - часть общего блока `common/stt/` (режим «файл»), не своё решение Scribe.
2. Этапы: звук → VAD (Silero, уже есть в `vad.py` и `multilang.py`) → куски ≤ 30 с по паузам → распознавание пачками (MLX: пакетный кодер, как уже сделано для языков в `MLXLID`; Windows / Linux - `BatchedInferencePipeline` faster-whisper) → говорящие по всему файлу → сборка.
3. Продолжение после сбоя получается само: готовые пачки пишутся на диск; после сбоя - «Продолжить (готово 64 %)», без вопросов о стыках.
4. **Без** ручного словаря терминов и **без** жёсткого ограничения памяти (практика не показывает выигрыша, есть риск упасть раньше): перед запуском - замок видеокарты и оценка свободной памяти (стандарт 2.4), при нехватке - окно, а не падение.
5. Прочь из кода то, что заменено, и временные файлы - убирать после готового результата (как служебные файлы Herald).
6. **Проверка до внедрения (A/B):** лекция Андрея 2 ч 57 мин и запись ~1 ч смешанная RU / EN - нынешний способ против нового: время, доля совпадающих слов, ошибки на знакомых терминах, говорящие (на записи с 2+ говорящими). Внедрять, только если новый способ не хуже по словам и говорящим и быстрее. Иначе - оставить один проход, добавить только продолжение после сбоя.
